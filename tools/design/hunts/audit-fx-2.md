# AU17 the rest of fx-thumbs, presets (save, apply, rename, delete), renamed-parameter migration

Branch `hunt/audit-fx-2`, against main fba44ca8 (v17.32). Labels: Measured / Read / Guess. Probes and raw output in `audit-fx-2-scripts/`. Headless Chromium, Linux.

## Findings
### AU17-1 (MEDIUM, fixed): the 121st saved effect preset silently deletes the oldest
- **Measured** (`presets.js`): 125 saves of a Blur preset leave exactly 120 stored; `p0` to `p4` are gone, the newest is first, and **no message was shown at any point** (the toast list stayed empty).
- **Cause (Read).** `FM.effectPresets.save` rebuilt the stored list as `readRaw().filter(not this id).slice(0, MAX_PRESETS - 1)` and then added the new one on the front: at the limit the slice drops the oldest. The same file says, two screens up, "a trimmed animation is recoverable, a discarded preset is not".
- **Fix** (`js/fx-presets.js`, buster 12 to 13): at the limit a NEW preset is refused with "You have 120 saved presets, which is the most FreeMotion keeps, delete one first" and the list is untouched; saving over an existing preset (same id) still works at the limit.
- **Proof.** `AU17-1`: 120 saves pass (control); a re-save of one of them at the limit replaces it (control); the 121st returns false, leaves all 120 including `p0`, and says something naming 120 and delete; after one delete there is room. **Red on main at 1280 and 380 ("the 121st preset was saved (and so one was dropped: p0 is gone)"), green with the fix at both; 2 mutations CAUGHT** (the guard off, the same-id exception off).
- **Neighbours:** `721` and `581` (the raw-store and container rules) pass at both widths. The `preset` and `resets` slices have 6 reds at 1280 that are **red on main too**, 3 of them with "no layer to work from" (the slice runs the test without its fixture layer; I believe they pass in the full run, Guess) and `the per-effect preset list says WHICH presets it means`.

### AU17-2 (guard, no bug found): nothing protects a renamed parameter
- **Measured.** A saved effect keeps only the parameter keys the registry knows: `{type:'blur', params:{radius:5, futureKnob:7}}` comes out with `radius` only, and an effect of an unknown type is dropped from the layer (`_sanitizeLayers`). The autosave then writes that back, so **renaming or removing a parameter key, or an effect type, would reset that setting (or lose that effect) in every saved project, silently.**
- **Read.** There is no param-alias table anywhere. The conventions that exist are different: the type id stays when a label is renamed ("the type id stays 'motionblur' so saved projects, presets and the AI vocabulary all still resolve", `compositor.js` 607), the one type rename that happened (`_objblur` to `objectblur`) got an alias in the favourites and recents lists only (`fx-browser.js` 183) and a flag-to-effect migration in `sanitizeEffects` for saved projects, and an absent key is covered by `legacy` (checked in AU16). Nothing has been renamed since that I could find, so this is a hole nobody has fallen into yet.
- **Guard.** `AU17-2` pins every one of the 206 effect types and 1,011 parameter keys that exist in v17.32 and fails, naming them, if any is gone: the moment to add an alias and re-pin. New types and keys are fine. Green on main by design (it pins what exists); **mutation CAUGHT** (a registry key renamed). It does not add an alias mechanism: I did not build one, because no rename exists to test it against.

## Presets: what I checked
- **Round trip (Measured, `presets.js`).** For all 178 effects: set the first three animatable parameters to keyframes (one with `loopMode: cycle`, one `pingpong`), capture, save, read back, apply with `makeInstance`, compare every parameter. **176 of 178 identical.** Not an exception: `copybg` captures nothing (it has no settings, by design) and `wiggle`'s `amounty` is absent from its default instance (it falls back to `amount`), which my first comparison tripped on.
- **Rename (Read).** Presets have no rename in `fx-presets.js`. The Presets card's "renamed" is the inspector's tag and rename layer (`inspector.js` 317 to 390, "a rename is therefore a RE-KEY"), which stores names beside the presets, not in them. `save()` with an existing id replaces a preset, which is what a rename through that route would do. I did not exercise the inspector's rename path.
- **Delete (Read).** `remove` is immediate and there is no undo and no confirmation (`fx-browser.js` 733: a tap on the drawn X removes the row and says "Preset deleted"). By design as far as I can tell; I list it because it is the only irreversible tap in the feature, and the fix above makes "delete one first" the way out of a full list.
- **Applying a preset made before a parameter existed (Read, not fixed).** `makeInstance` starts from the registry's defaults and overlays what the preset holds, so a parameter the preset predates gets the NEW default, where a saved project that predates it gets its `legacy` value (AU16: 16 effects differ, e.g. Shake amount 20 versus 120). The comment says that is intended ("forward-compat"). For a custom preset saved long ago it means it can look different from when it was saved. I left it: it is a looks decision.

## fx-thumbs: what I checked, and what I did not read
- **Read:** the cache and queue code (about 1,028 to 1,160, 1,255 to 1,300, 1,435 to 1,560, 1,660 to 1,828) and the no-op probe (AU16). **Not read:** the sample-subject and photograph tables, the OVERRIDES demo tuning, the layer strip stepping (`layerStep` beyond its first 60 lines) and the filmstrip-like job code. That is roughly 800 of the 1,828 lines.
- **Measured, `thumbs.js`:** 240 layer-preview mounts over 12 revisions of one layer: the byte-capped cache held at **9.87 MB of a 10.49 MB cap** (14 entries), and the queue drained to 0 queued, 0 pending, 0 jobs. After the canvases were removed and `stopAll()` called: nothing queued or running; the cache keeps its 14 entries (the documented 10 MB session cap, not freed). A job mounted for a layer that is then deleted does not throw; it leaves one cached entry (tiny, inside the cap).
- **Read, not measured:** `sceneRev` hashes the whole layer list with `JSON.stringify` once per task, so every edit anywhere invalidates every layer tile (by design, stated in its comment) and costs time in proportion to project size (PF1's project is the case to try); the cache and `meta` map are bounded by the cap and the catalogue.
