## Three findings, each red on main, green with the fix at 1280 and 380, mutation-caught

**AU23-1 (Measured): an admission can file the room under the wrong project.** `saveRoom(pid, room)` writes `localStorage['fm.collab.host.' + pid]`. The S6 review fixed a bug where the module's `hostRoom` outlived its project by adding `hostRoomPid`, and most saves read `hostRoomPid || currentPid()`; **four did not** and read `currentPid()` (the member-role note, the "When someone uses the link" switch, Reset, and the admission itself). If the owner has switched projects when one of those runs, this room's link, key, code and member list are written under the OTHER project's key, so a project that was never shared now looks shared, and opening it offers to resume somebody else's room. Measured through the real flow (`relayHost921`, a joiner's knock, the owner taps Let in) with the current project switched mid-knock: `fm.collab.host.<other>` appeared holding this room. Fix: the four sites use `hostRoomPid || currentPid()`. Test `AU23-1` (the admission, red on main), `AU23-2` (the switch, red when its site is mutated back); the other two sites (role note, Reset) share the one-word fix and are not each driven by a test.

**AU23-2 (Measured): see AU23-1**, the same fix proved at a second site.

**AU23-3 (Measured): a collaboration name can be cut in half an emoji, and can carry a direction override.** `cleanName` (the rule every name passes through, the profile's and a joiner's) strips C0 and C1 controls, trims and does `slice(0, 32)`. A name that reaches the limit inside a surrogate pair ends in a lone high surrogate (measured: `'a' + 39 x 😀` came out 32 units ending U+D83D), which the wire turns into U+FFFD; and U+202A to U+202E and U+2066 to U+2069 (override, embedding, isolate) are not controls, so a joiner can name themselves so that the people list reads backwards or reorders its neighbour. Fix: drop those nine code points and never leave a trailing lone high surrogate; the joiner U+200D (emoji sequences) and the marks U+200E/F (right-to-left names) stay. Test `AU23-3`: red on main; mutations (no surrogate trim, no bidi strip, a strip that eats U+200D) each CAUGHT, the last by the control.

## Read, not fixed (judgement, with the line)
- **Save points and a clock that goes backwards** (`checkpoint`, line 891): keys are `collab:ckpt:<pid>:<ms>` and the trim deletes the lowest keys. `lastCkTs` keeps keys rising within one page's life, but it starts at 0 on every load, so after a reload on a device whose clock has gone back (a phone corrected from a wrong date), the new save point sorts BELOW the old ones and the trim deletes it first. Needs: the clock moved back past the newest save point, ten or more save points. I did not build the repro (a Guess for how often).
- `loadRoom` assigns `r.settings.ask = true` (a strict-mode write) after `r.settings = r.settings || {}`; a hand-edited record whose `settings` is a string would throw there. localStorage is the app's own, so unlikely.
