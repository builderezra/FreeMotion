# AU3: audit of js/storage.js on main v17.31 (3,778 lines), save / reopen / upgrade / quota paths first

Against `origin/main` 7125ecff. Branch `hunt/audit-storage`. **Measured** = I ran it here (headless Chromium, the suite's own driver, 1280 and 380), **Read** = I read the code, **Guess** = I did not check.

**Bottom line, honestly.** The save path itself (`writeScene`, the rev guard, the quota refusal and the "would this change anything" skip) held up: I read it line by line and found nothing that loses work. What I did find is on the other side of it, **what happens to a document that is not exactly what this build wrote**: a stored project that will not open, a boot sweep that deletes a damaged project's clips, and one decision that needs him. Five items are fixed and proven; one is measured and left for a decision.

## Measured, not fixed: needs his decision (AU3-5)

**Opening a project in a build that does not know one of its effects throws that effect away, and the next autosave makes it permanent.** `sanitizeEffects` (:1417) runs on every load and keeps an effect only if this build's registry has its type, and keeps only the parameters this build's registry lists, clamped to this build's ranges. In `au3-needs-decision.js` (**Measured**), a stored project with an effect of an unknown type loses it after one open and one save; the unknown parameter's loss is **Read** from the same function (`sane()` copies only the registry's own keys), not run. It matters in exactly the scenario this repo has a script for: `tools/rollback.sh` puts an older build live, and every project he opens on it quietly loses whatever the newer build added, with no toast, and the autosave writes the loss back. The same applies to a `.fmotion.json` from a newer build opened on an older one, and to a second device on an older cached build.

It is by design that an unknown type is dropped (a type is a key into six render tables; the comment says so). The choice for him is what to do instead, and I did not pick: (a) keep it as is and accept the loss; (b) **keep unknown entries, disabled, in a side list that is saved with the layer** (not an underscore key, which is never saved) and put them back in the stack when a build that knows them opens the project: no loss, a small amount of code in the sanitiser and the load; (c) refuse to autosave over a document written by a newer build (the doc already carries a rev; it would need a build stamp) and say so. I would build (b); (c) is the cheapest safe step. **Guess:** how often a rollback really happens; I did not look.

- A refused scene write followed by "Storage full" every tick: queue 748 fixed that, and the test covers it.

The toast then says "an older copy" which is the wrong sentence for this case, a wording issue only.
