# Phone performance hot paths (H6)

Against `origin/main` b46b47d (v17.23). Report only: no app or test code changed, **nothing was run or timed in a browser for this**. Every cost below is *reasoned from the code*, with counts I could read. Where I say a size, it is a guess unless a script computed it.
**Read** = I read the line. **Guess** = depends on a real device.

The shape of the finding: **the preview render itself is the most-optimised part of the app (the ladder, the GL warp and colour paths). The waste is in the DOM bookkeeping that runs on every animation frame around it**, plus a few things that run on a timer while editing. Ranked by (cost per frame or per edit) × (how often) × (phone CPU).

## Corrections (7 Oct, after the PM check; the report below is left as written)

Line reference: **items 1 to 5 run at `js/app.js:2505-2506`**, after the `if (fno !== _lastDrawnFrame)` block (`:2485`), not at the `2487-2488` I cited. Several costs below are overstated because writing an unchanged value costs little; the measured-in-code claim is "runs every rAF", not "is expensive". Nothing here was timed.

1. **Item 1 (`updatePlayhead`).** Confirmed: every rAF, `querySelectorAll` at `js/timeline.js:5843` and `:5846`, a linear `FM.layerById` per clip (`:5847`; `js/scene.js:833-835`, so O(clips × layers) per frame), label writes at `:5872` and `:5882`. **Overstated:** `label.style.left` is constant per clip and a same-value inline style write does not invalidate style, and `classList.toggle(token, force)` does nothing when the state already matches. **The real costs are the O(n²) lookup and the `maxWidth` write** (`:5882`), which depends on the scroll position so it changes every frame while scrolling. "Largest" is unmeasured. The fix holds (a clip-to-layer Map built in `rebuild()`, `maxWidth` only for clips intersecting the viewport and only on a change of 1 px or more). For the test use a `MutationObserver` count or a timing at 30 clips, and assert a large drop, not near zero (same-value writes can still produce mutation records).
2. **Item 2 (`syncKeyRail`).** It does run every rAF (`js/timeline.js:5812`), but almost every write repeats the previous value: `--insp-extra` (`:5784`) changes only when `shown` flips, so the claimed per-frame subtree invalidation **does not happen**. What remains is JS work, string building and same-value attribute sets: real but small. **"Medium" is overstated.** A point I missed: `syncKeyRail` writes before `updatePlayhead`'s deliberately read-first layout reads (`:5833-5841`, the queue 387 ordering), so on a crossing frame its class toggles can force a synchronous layout. **The signature early-return is correct** (`(n, side, view, inBrowser)` plus the selection ids), and **also move the call to after the geometry reads.**
3. **Item 3 (forced layout in `canvas-edit`).** The read-after-write pattern is confirmed (`js/canvas-edit.js:862-937` writes, then `placeRotKnob` `:945` `classList.remove` and `:946` three `getBoundingClientRect`, from `render()` at `js/app.js:126`). **"Every render" is too strong:** with a still layer and the knob on the stage, every write repeats the old value and the rects come from clean layout, which is cheap. **Two cases are worse than I wrote:** (a) any selected layer that moves forces one synchronous layout per drawn frame; (b) when the knob has been relocated because it would sit off the stage, the `remove` at `:945` dirties layout before the reads and the `add` at `:953` dirties it again after, so `updatePlayhead`'s `clientWidth` and `scrollWidth` reads then force a second layout in the same tick. Case (b) is the one the function's own comment calls typical on his phone (a portrait clip filling a 9:16 project). **Fix:** cache the box signature (w, h, cx, cy, rot, skew, shift) plus the stage rect and skip `placeRotKnob` when unchanged; toggle each knob class only when the decision changes, with no remove-then-add. **Test:** spy on `Element.prototype.getBoundingClientRect` over 60 frames, once with a still layer whose knob is relocated and once with an animated layer.
4. **Item 4 (`updateReadout`).** The title is rebuilt and written every call (`js/app.js:732`), with two `markers.some` and a `getElementById`. But the heavy parts are **conditional**: `syncTransform` (`:761`, `js/inspector.js:5388`) returns at once unless the Move & Transform panel is attached; `refreshEasing` (`:765`, `js/graph-editor.js:567-571`) redraws only when the easing canvas is in the document; `syncPlayhead` (`:764`, `js/inspector.js:6997-7002`) rebuilds only on a crossing. "The whole inspector sync every frame" is true only with those panels open. Set `readoutEl.title` on change, not per call.
5. **Item 5 (display rate versus draw rate).** Confirmed, at `js/app.js:2505-2506`. The fix stands: inside the draw check run `updateReadout` and `updatePlayhead`'s clip loop, keep only the `scrollLeft` write per rAF (plus `maxWidth` if the label cap must follow the scroll smoothly).


## The per-frame path (what runs 60 times a second during playback)

`tick()` (`js/app.js:2442`) does, **every rAF**, outside the "draw only if the project frame changed" branch:
`FM.timeline.updatePlayhead()` and `updateReadout()` (`js/app.js:2487-2488`). The author's own note in `updatePlayhead` says it runs twice per drawn frame of a 30 fps project (measured by them, "180 calls to 90 renders", `js/timeline.js:5815-5820`). Everything in items 1-5 is multiplied by that.

## Preview size (a note, not a finding)

The preview scale is `cssW × dpr × zoom / project width` (`js/app.js:564`), so at zoom 1 the canvas is about **screen resolution**, not 12 MP. The `MAX_PREVIEW_PX = 12e6` cap (`js/app.js:148`) only bites when zoomed in. For scale: a 440×956 phone at dpr 3 has 3.79 MP of screen (computed with a script), so the cap is 3.2 times the screen. Whether zoom renders the whole frame or only the visible slice depends on `previewCrop` (`js/app.js:587`), which I did not trace to the end. **Guess** only.

## How to prove each one (so it cannot creep back)

- Items 1-5: a test that plays 1 s with 30 clips and counts `style` and `classList` mutations with a `MutationObserver` on the lane. Today: a count proportional to clips × frames. After: near zero for a still timeline. The suite already has the pattern `tests/_playcost.html` (cited at `js/timeline.js:5817`).
- Item 3: count `getBoundingClientRect` calls during 60 frames of playback with a layer selected (spy on `Element.prototype`). Today 3 per frame; after, 0.
- Item 6: see `app-memory.md` §5.
- Each test must fail against HEAD source (the `tools/prove.sh` rule).
