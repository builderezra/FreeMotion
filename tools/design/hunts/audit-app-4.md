## Finding AU13-1 (MEDIUM): Add text, then Undo, loses the layer for good and leaves a dead Undo
- **Measured.** `FM.addTextLayer()` (it opens the text editor), then `FM.history.undo()`: the layer goes (correct), but `canRedo()` is false and `canUndo()` is still true; a second Undo does nothing visible. A shape does it right.
- **Cause (Read, and measured by logging every history commit):** Undo calls `textEdit.flush()`, restores the earlier state (the text layer is gone), `refreshAll` runs `textEdit.syncToSelection()`, which sees the editor's layer is no longer selected and calls `commit()`, which pushes a new history entry. A push after an undo discards the redo stack, and the pushed entry is the spare one.
- **Why it is not by design:** the comment on `syncToSelection` says commit is for "tapping off the editor" so typed words are not lost; with the layer gone there is nothing to write. (`text-edit.js` is outside app.js; I found it through `addTextLayer`, so I read only `commit` and `syncToSelection`.)
- **Fix** (`js/text-edit.js`, buster 26 to 27): in `syncToSelection`, if `layer()` is gone, tear the editor down without committing.
- **Proof.** `AU13-1`: shape control (add, undo, redo), then text: Undo removes it, Redo exists and brings it back, a further Undo/Undo does not find a spare entry. Red on main at 1280 and 380 ("after Undo of an added text layer there is no Redo"), green with the fix at both. Mutations CAUGHT: guard disabled, commit put back. Neighbours: the `text edit` (17) and `523` slices green at both widths; the `Undo` slice has two reds (`690 a project renamed on Home…`, `690 Undo and Redo keep open the effect…`) that are red on main too.
- **Not covered:** a collab peer deleting the layer under an open editor takes the same path (Read, not run).
