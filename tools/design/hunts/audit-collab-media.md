# AU21: collab media (a clip, a picture or a song between peers on the fake network) and the boot-time touch wiring

Branch `hunt/audit-collab-media`, against main v17.33. Labels: **Measured** = ran it, **Read** = read the code, **Guess** = not verified. Fake network only (`withCollab921`'s loop link and the in-page test peer); no real relay or WebRTC. Headless Chromium, Linux, 1280 and 380.

## Two real bugs, both fixed, both with a test red on main and green at 1280 and 380 and mutation-caught

### 1. A guest who drops mid-upload and comes back never finishes its clip on the host (Measured)
- **Repro.** The host receives a guest's 9 MB picture; the guest's link closes after 55 % (the app calls `dropPeer`, `collab-ui.js` 2871); the same guest comes back on a new link (a **new member id**, `m1` then `m2`) and offers the same file again. **The host never sends a second `want` (0 wants), the clip never arrives (40 s), and the whole time the export question counts it as arriving: `pending {n:1, pct:50}`, `inb:1`, and the byte total doubles on the re-announcement** (`pending 36 %`).
- **Cause (Read, confirmed by the measurement).** Both ends of a transfer name the member on the other end and neither was released when that member went. On the receiving side `ctl.inb[fid]` and `ctl.wanted[fid]` stay, and `planWants` has `if (ctl.inb[fid]) { want += e.size; continue; }`, so nothing is ever asked again. A guest that receives from the host is not affected (its controller is built fresh on every rejoin, which is why the existing resume test has to reset `inb` by hand).
- **Fix.** `M.forget(S, mid)` (called from `dropPeer` and from a member's `bye`) now marks every file that member was the source of as "no longer has the bytes" (the same `miss` state a `miss` answer sets), aborts that file's inbound transfer and takes it out of `wanted` and the queue. The parts on disk stay, and the guest's next announcement of the file clears `miss` and resumes from them.
- **Test** `AU21 a guest that drops mid-upload and comes back finishes its clip on the host, from the bytes already kept`: after the drop and a full sweep (2.4 s) nothing is pending or in flight; the returning guest is asked from the byte offset the parts hold (not 0); the 9 MB clip arrives byte-identical. **Red on main** at both widths ("the host still counts the clip as arriving (1 pending, 1 in flight) from a member that has left"). **Mutations CAUGHT:** the inbound abort removed; the `miss` flag removed (this one SURVIVED the first version of the test, which looked too early; it now waits past a sweep); the clearing of `miss` on a new announcement removed.

### 2. A member who leaves leaves its send loops running (Measured)
- **Repro.** A guest wants two 9 MB clips and then stops acknowledging (a receiver that aborted, or one that has left). After 4 s the host has **two jobs at 8,454,144 bytes sent past `upto` 0, `stop` false**, each waking every 25 ms (the send window brake, `serve`, collab-media.js 899 to 905); a **third file the same member asks for is ignored** (`live >= IN_FLIGHT`, no T_START ever arrives); and **after the member is dropped (`dropPeer`, link closed) both jobs are still there, 3 s later**, until the room ends.
- **Cause (Read).** `serve` ends on `stop`, a failed `sendBulk` or the end of the file. A receiver gone quiet is none of those: it is the window brake, which sleeps and re-checks for ever and never reaches `sendBulk`. `M.forget` only dropped `told[mid]`.
- **Fix.** The same `M.forget`: jobs addressed to that member are stopped.
- **Test** `AU21 a member who leaves does not leave send loops running behind it`: both jobs reach the window brake, the member is dropped, the jobs are gone inside 3 s. **Red on main** ("2 send job(s) still running for a member who left"), green with the fix at both widths, **mutation CAUGHT** (the stop removed).

## Audited and clean (Measured)
- **Chunk, part and window boundaries.** A real, decodable PNG padded to **65,536; 65,537; 4,194,303; 4,194,304; 4,194,305; 8,388,608 and 8,388,609 bytes** (one chunk, one over, one part minus one, exactly one part, one over, two parts, window plus one) arrives byte-identical, is written to the receiver's own record, and **leaves no part behind** (`AU21 files that end exactly on a chunk, a part and the send window…`, green on main as well: it is coverage, not a repro).
- **Resume after a drop, a big file, a link cut mid-file, a font, a full device, a replace and its undo, two uploaders at once, a 90 MB font, a peer naming another project's layer**: already covered by the 28 `921 S4` tests. The slice is **25/26 on the branch and on main** (the one red, `splash.mp4, a PNG and a WAV…`, is this container having no H.264). `921 S2` is 33/33. `921 S8` is **30/31 on the branch and on main** (the one red is `[Scan QR]`, the container has no camera). The branch's first S8 run also failed `adversarial peer fuzz` on a timing assertion ("one round of hostile messages held the owner’s main thread for 500 ms", a round of `ctl`/`pres`/`bulk` junk that does not touch the media controller); that test passed alone on the branch and on main, and the whole slice passed on a re-run, so I call it a load flake and record it rather than hide it (`results/final_s8_1280.txt`, `final_s8_1280_rerun.txt`, `main_s8_1280.txt`).
- The receiver's own records (Read, and the boundary test): `writeRecord` stores the file, decodes it, and sets `rev`; `applyFile` skips a layer whose `mediaRev` has moved past the file (the late-arrival rule) and one that is not in the open document.

## Read, not fixed
- **An aborted transfer is not cancelled on the sender.** There is no message for it (`want`, `ok`, `have`, `mf`, `ann` only). When the RECEIVER aborts and stays (`outOfRoom` on a full device, `offset`, `oversize`, `gap`, `read`), the sender's job stalls at the window and polls every 25 ms until the member leaves (now ended by fix 2) or the receiver asks for the same file again (which supersedes it). A `{t:'stop', xid}` from `abort()` would end it at once; it is a protocol addition, so I left it for you. A job that stays also holds one of the receiver's two in-flight slots, which matters only after two such aborts for files it then never asks for again.
- **A manifest entry of size 0 would never complete** (`complete` runs only from a data frame). A zero-byte clip cannot be imported (it does not decode), so I could not reach it.
- **A clip whose only source has left** is left blank on the host: with the entry marked missing it is neither "arriving" nor marked on the timeline. The old state (a frozen progress bar) was wrong, but what the clip should look like now is a design call.

## Boot-time touch wiring (Read only; finger repros are NOT RUN here)
Read: the splash boot script in `index.html` (`pointerdown` with `preventDefault` then `dismiss(true)`, the permanent `keydown` listener, the 5 s hard cap, `gone` guarding every path), `js/mobile.js` `makeSwipeDown` (the `window` `pointermove` listener is non-passive for the whole session but only acts while a swipe is claimed; second finger ignored; `pointercancel` snaps back and never dismisses; the `_fxReordering` guard) and the non-passive `touchmove` listeners in `js/home.js` (each exits at once unless a pull is live). I found nothing to fix there that is not already in `hunt/audit-mobile` (#1109's two swipe bugs, AU7). The permanent `keydown` listener on `document` keeps a closure alive for the session; harmless, noted.
