# FZ1: why `921 S1 convergence fuzz` fails other seeds on main

Against `origin/main` 1fa76385 (v17.34). **Measured** = I ran it (headless Chromium on Linux, 1280 and 380), **Read** = read the code, **Guess** = not checked. Branch `hunt/fuzz-seeds`; scripts and per-seed results in `fuzz-seeds-scripts/`.

## The short answer
**Two real devices CAN end up with different projects, but only in one narrow case, and the fuzz was hiding a second, harmless reason behind the first.** Of the seven seeds from the E1 finding (23, 28, 30, 32, 38, 39, 43):
- **Six (23, 28, 30, 32, 38, 39) are the fixture, not the product:** two devices minted the same layer id.
- **One (43) is a product bug**, found only after making the fixture model what a real guest does. It also explains five more seeds that fail beyond the 43 (68, 107, 117, 119, 138).
- The pinned seed `20260923` passed on main only because it never reached either.

## How I tried other seeds (the seam)
`?seed=N` on `tests/run.html` picks the seed of the pinned test (the test frame cannot read its own query, so it reads `window.top.location.search`; the first version read the frame's and silently ran the pinned seed every time, which is why a first sweep reported "all pass"). Default unchanged.

## Shape A, seeds 23, 28, 30, 32, 38, 39: the same layer id was minted twice (fixture)
Failure texts: `layers/7/parent ("add_3qd_1" vs null)`, `layers (length 21 vs 20)` (28, 30, 32, 38), `layers/0/transform/x` (39). In every one the owner's tree held **a duplicate id** (`dupOwner: ["add_5en_0"]`, seeds 28, 30, 38 all the same id; 32: `add_1v7_0`) while the host's base held one copy. The fixture's `mutate921` names an added layer `'add_' + seed.toString(36) + '_' + r`, and the owner's mutation seed (`round*31 + a*7 + 1`) and a guest's (`round*37 + a*11 + 3`) coincide for some pairs of rounds (the owner at round 226 and a guest at round 189 both give 7007 = `5en`). Two devices then create the same layer with the same id, the host keeps one copy, and the fixture's owner applies the other as a second copy. **A real device cannot do that:** `uid()` in `scene.js` ends in five random base-36 characters (60 million values) on top of a counter and a clock. Fix: the device tag goes into the id in the fixture (`mutate921(doc, seed, rounds, tag)`). With it, 23, 28, 30, 32, 38 and 39 pass and nothing else in the scenario changes.

## Shape B, seed 43 (and 68, 107, 117, 119, 138): a tx whose ack died with the line, replayed after somebody else changed the same thing (PRODUCT)
Seed 43: `layers/11/transform/x (130.741 vs 288.519)`, guest 3 holds the older number. The trace (`results`, `scripts`): g3's tx moved a layer (host seq 49), g3's line dropped before the ack arrived, g2 then set the same value (seq 74), g3 reconnected through the **tail** and replayed. Two things in the real code combine (Read, `collab-session.js`): on a tail, `onBatch` skips a remote value for a path this device still has **pending** (its own tx is unacknowledged), so batch 74 was skipped; then `replayOutstanding()` resends the tx and the host answers a duplicate with its **cached ack** (`collab-host.js` §7.1 step 3), which carries the values THAT tx wrote, and the guest applies it as its own ack: the older value goes back over base and screen. Nothing sends the newer one again, so the two disagree until §11.4's hash notices, and the hash is skipped while the guest has anything outstanding or the host is not quiet (`onHash`, `maybeHash`), so **a guest that keeps editing is not healed**.
- **Why the fuzz missed it as a product bug:** its guest model (`guest921`) kept only txs made while OFFLINE in its outbox. A tx sent online whose ack was lost was forgotten, so the guest ended with the value in its base that the host never saw, a different divergence, and it hid this one. The real Session keeps every unacknowledged tx in `outstanding` and replays it. The fixture now does the same (`g.inflight`), which turns seed 43 green on its own, and then needs the host fix below for the replay case (the five beyond-43 seeds each show the same family: a stale `li`, `ai` or order statement coming back in a replayed ack).
- **Deterministic test** (`FZ1 a tx whose ack died with the line…`): g3 sends, loses the ack, g2 changes the same value, g3 reconnects through the tail and replays. **Red on main** (g3 holds 111, the host and g2 222), green with the fix.
- **Fix (`collab-host.js`, `refreshDup`, `?v=5` to `6`):** the answer to a duplicate tx is the cached ack **refreshed**: for every `s`/`d` whose path no longer holds what the tx wrote, and for every structural op (`li lr mv ai am ar`) it carries, the host's present state is appended to the repair, under the same per-tx and per-member budget a refusal's repair uses (what does not fit becomes `resync: 1`, the budgeted copy), and the cached ack's stale `ord` order statement is dropped. Not a new channel: the guest already applies `ack.ops` then `ack.fix`.
- **Tests, all red on main and green with the fix at 1280 and 380:** the scenario test; `FZ1 the refreshed ack of a replayed tx is budgeted…` (five later 150,000-character bodies: the repair is held to 512 KB and says `resync`); and `FZ1 the convergence fuzz holds for the seeds that once failed` (23, 28, 30, 32, 38, 39, 43, 68, 107, 117, 119, 138 in one test, 60 s). The pinned fuzz is now `convergenceFuzz921(seed)` and still runs its own seed.
- **Mutations (Measured, each CAUGHT):** serve the cached ack unrefreshed (scenario and battery red); keep the stale `ord` (battery red at seed 119); refresh only `s`/`d` (battery red at seed 68); drop the budget (budget test red).
- **How often can this happen to a person?** Needs all of: a line drop between a guest's edit being sequenced and its ack arriving, somebody else changing the same value or element before the guest is back, and the guest coming back through the tail rather than a snapshot. Rare, but connections drop on phones, and the damage (a layer's position or an effect list differing between two people until one of them reloads) is the kind that looks like "the app lost my change". **Measured:** 5 of the first 150 seeds hit it beyond seed 43.

## What is left
- **Seed 142 still fails (1 of 150 with the fix): `project/comments (length 44 vs 45)`.** The trace shows guest 1 resending `s P/comments` (the whole list) again and again, 2 s apart, 8 times in a row, each answered with one repair op and no progress. Host rule "a guest's whole comment list, where base already has one, becomes inserts" refuses some insert (`goneRefused` or a limit) and the fixture guest never converges on the list. I did not take it to a root cause; it may be a real livelock if a comment can ever lack a valid key (the comments UI always gives one), or the fixture's `mutate921` comment kind writing a whole list a real client never writes. Needs its own look.
