## #1086 Export: one clip's sound fails to read, the file goes out without it, and the card says "Sound ✓"
- **Claim: Verified (Measured).** One good clip plus one whose file will not decode: `run()` returns `hasAudio: true`, `audioDropped: null`; the mixer names the loss (`FM._lastAudioDrops` = `["bad clip (its audio would not decode)"]`, and the amber line is written to `#export-note`, which the ready card then hides behind itself), and the card reads **Sound ✓**.
- **Callers traced (Read).** The drop list is written in `buildAudioMix` (`exporter.js` about 540 to 790); `audioDropped` is set only when NOTHING made it into the mix (`'all-unreadable'`, `exporter.js:748`). `run()` hands `{hasAudio, audioDropped}` to `onReady`; the only reader is `showExportReady` (`app.js:6280`). The audio-only path reads the same list for its own toast.
- **Patch.** `run()` adds `audioMissing` (the length of `FM._lastAudioDrops`, when there IS a mix) to the result; the card's sound line moves into one function (`exportSoundText`, with a suite seam) and reads **"Sound — 1 clip missing"** (plural for more), tinted like NO SOUND. The PM's item 3 in the entry ("do not treat a missing AAC description as encode-failed") is respected: nothing here touches that.
- **Test.** `P22 #1086`: one good clip reads "Sound ✓" (CONTROL); add one that will not decode: `hasAudio` true, `audioDropped` null, the mixer names the bad clip, and the card text is "Sound — 1 clip missing", not a tick. **Mutations:** the card ignores the count (A1), `run()` never reports it (A2): both CAUGHT.
- **Open choice (ask):** the wording and the tint. I reused the NO SOUND tint (it IS partly no sound); a softer amber for "partly" is one CSS class. **Also counted as missing:** a clip that sits outside the exported range of a WHOLE-project export (the mixer lists it too, and it is a real loss).

## #1087 Export decodes each source file whole, with no size ceiling
- **Claim: Verified (Read plus Measured).** `buildAudioMix` calls `FM.decodeAudio(m.file)` with no size check (`exporter.js` about 562), while the waveform, the audio probe and the import from video all refuse a source over `WAVE_MAX_BYTES` (300 MB, `media.js:917`). After the export nothing lets the buffer go (Measured: after a mix the clip's record still held 44,099 samples for a one-second source; for a 4-minute stereo song that is about 90 MB, the number in `audio-tools.js`).
- **Callers traced (Read).** The decode is in `buildAudioMix`, called by `run()`, by the audio-only export (`app.js`), by the suite. Readers of `m.audioBuffer`: `audio-react.js:43` and `audio-tools.js:28` decode lazily when it is `undefined`; `app.js:2629` decodes a REVERSED clip's buffer ahead of play when it is `undefined`; `audio-play.js:26` plays a reversed clip from it; `media.js` keeps the 8 kHz probe OFF this slot on purpose. So putting a decoded buffer back to `undefined` is what every reader already treats as "not decoded yet".
- **Patch.** (1) On a touch device (no fine pointer with hover: the same test `FM.frameCacheLimits` uses) a source over `WAVE_MAX_BYTES` is not decoded: it joins the drop list as "too big to read its sound on this device" (so the card from #1086 says so). A desktop keeps decoding it. (2) The sources a mix decoded are flagged and put back to `undefined` as soon as the mix is built, on every exit; a REVERSED clip keeps its buffer (the PM's exception) and a buffer some other reader decoded earlier is never touched. The PM's "do NOT decode at 8 kHz" is respected.
- **Test.** `P22 #1087` (phone simulated by replacing `matchMedia`): a small real WAV on a touch device builds a mix (CONTROL); its buffer is not kept; a reversed clip keeps its buffer and an already-decoded one is untouched; on a desktop an oversized source is still decoded (CONTROL), on a touch device it is named and not decoded. **Mutations:** release never runs (B1), reversed released too (B2), foreign buffers released (B3), no ceiling (B4), ceiling on desktop too (B5): all CAUGHT.
- **Risks.** An iPad with a keyboard reports a fine pointer and so decodes whatever it is given (**Guess**: acceptable, but it is the device class this protects). Audio-react is not exempted (the PM's list names it): its buffer is re-decoded the next time something asks, one decode per ask; I judged that cheaper than a flag nothing else needs. **Also found, not changed:** `FM.decodeAudio` catches every error and returns `null` (`media.js:843`), so the `catch` around it in the mixer is almost dead and a corrupt file reads as "its audio would not decode" with no browser message.

## #1088 Audio-only export: no fresh tap, the file revoked after 1 s, and "Audio exported" whatever happened
- **Claim: Verified (Measured on the Chromium side; the iPhone half is the entry's, Guess here).** The audio export mixes (minutes on a long project), then clicks a programmatic `<a download>`, revokes the URL 1 s later and toasts "Audio exported" at once (Measured: with the click stubbed, the file went out immediately with no card and the toast came before anything was handed over). On Safari a download triggered long after the tap may be refused, and nothing says so.
- **Callers traced (Read).** One writer: `runAudioOnlyExport` (`app.js:5950` to `6006`), reached from the export dialog's `runExport` (`:6111`). The video path already has the right shape: `showExportReady` shows a card whose Save is a fresh tap that calls `deliver()` (share sheet where it exists, else a download), and a dismissed sheet keeps the card.
- **Patch (the PM's first option).** `deliver(blob, name, type)` takes a type (it hard-coded `video/mp4`) and is exposed as `FM.exporter.deliver`; the audio export now hands its file to the same card (`audioOnly: true`: the meta line reads "1.2 MB · 0:02 · audio only", no picture size or frame rate), saves through `deliver` with `audio/wav` or `audio/mp4`, and says **"Audio saved"** only after a real hand-over (not for Discard, not for a dismissed share sheet). If the card is missing from the document it falls back to the old click with the URL kept for 4 s (the PM's stopgap).
- **Test.** `P22 #1088`: the file is NOT downloaded straight away; the card comes up with a `.wav` name and "audio only" in its meta; a dismissed share sheet keeps the card and says nothing; Save closes it, hands a `.wav` with type `audio/wav` to `deliver`, and says "Audio saved"; Discard delivers and announces nothing. **Mutations:** the old straight-download path (C1), "saved" said without a hand-over (C2), the wrong MIME type (C3): all CAUGHT.
- **Not run:** a real iPhone (does `canShare({files:[audio/wav]})` answer true there, and does Save show the share sheet?). **Open choice (ask):** "Audio saved" against the old "Audio exported" wording.

## #1089 Phone memory: four things that never shrink
The entry lists four; two are done and proven, two are plans with measurements.
1. **The card thumbnail's canvases (patch + test).** `makeThumb` draws the whole project at full size (1080x1920 is about 8 MB) plus three smaller stages and never zeroes any of them. **Measured: four canvases (1080x1920, 540x960, 270x480, 203x360), 10.7 MB, all still holding pixels after the call.** It runs on every autosave tick (12 s), every import and every Home visit. Patch: each finished stage and the last canvas are set to 0 x 0 once the data URL exists. Test `P22 #1089`; mutations D1 (first stages kept) and D2 (last kept): both CAUGHT. **Not done:** the entry's "render at 2x the card size" (it needs `renderScene` to draw scaled; **Guess**: one transform on the context, but I did not try it, and it changes what the card looks like).
2. **Decoded export audio (done, it is #1087's release).**
3. **The compositor's scratch pools (plan, measured, NOT built).** **Measured: rendering one frame of a 1080x1920 project with 12 effects (glow, blur, drop shadow, vignette, wave, tilt shift, mosaic, edge, motion blur, zoom blur, pixel sort, halftone) leaves 25 canvases all holding pixels, 159 MB, plus the 7.9 MB `_fxScratch` array,** after the render finished. There are about 30 module-level pools and singles in `compositor.js` (`_ckCanvases`, `_lkCanvases`, `_grCanvas`, `_fbCanvas`, `_maskCv`, `_pmPool`, `_mbPool`, `_pfPool`, `_fcPool`, `_fxScratch`, `_gsBuf`, `_wpPool`, `_sqPool`, `_dspPool`, `_cfPool`, `_expPool`, `_t3Pool`, `_dfPool`, `_miPool`, `_pxPool`, `_blendMaskCv`, `_fbPool`, `_manualCv`, `_olPool`, `_adjCv`, `_adjTmp`, `_adjFcPool`, `_adjCssPool`, `_adjCssOut`, `_camCv`, `_mgPool`, `_measCanvas`). Plan: `FM.releaseCompositorScratch()` zeroes every canvas in them and truncates or nulls each; called in the `finally` of `run`, `runGif` and `runFrames` and on a project switch (beside `FM.releaseProjectMedia` in storage). Pools are rebuilt lazily by their `if (!pool[d])` guards. **Why I did not build it:** the temporal ones (`_ckLasts`, `_lkLasts`, the motion-blur accumulator, `_fbAvg`) carry state across frames, so the next render starts cold; that is right after an export (`prepareCaches` already wipes temporal state before every export) and on a project switch, but it needs a reviewer's eye on each of 30 variables, and a test that renders before and after a release and compares the pixels. I would build it after #1085's guard exists, so the saving can be shown.
4. **A global cap on the reverse and frame-blend caches (plan, NOT built).** **Read:** `prepareCaches` passes a flat `maxBytes: 1610612736` (1.5 GB) to EVERY clip that needs a cache (`exporter.js:1033`), not device-aware and not shared, so two long reversed clips ask for 3 GB. The preview side already has `FM.frameCacheLimits()` (a device budget, 128 to 384 MB). Plan: one budget per export, device-aware (the same limits function, scaled up for export), handed out as a shrinking remainder (`maxBytes: Math.min(perClip, remaining)`), so a second clip trades temporal resolution (`effFps`) instead of memory. **Ask:** the numbers (I would start at 384 MB total on a touch device, 1.5 GB on a desktop). **Not tested:** it needs two multi-hundred-MB clips; I cannot make those here.

## #1085 The test page reserves about 8.7 GB over one suite run
- **State.** The 8.7 GB is `VmData` (reserved address space), not resident memory (the PM's 7 Oct note), which changes what a guard must measure: RSS falls on a Mac exactly when memory is short. The entry's own measurements (7 Oct) say the biggest contributor is an APP leak (#1095, the effects browser, about 2.2 GB), then the splash film (#1096); two fixes and a half-built guard sit on the Mac's local branches `suite-mem2` and `suite-mem-fix`, not on GitHub.
- **What I could add and prove here.** The PM names the real 1080x1920 sweep: `692: every crop-admitted kernel draws the same picture cropped…` builds a fresh 1080x1920 `Uint8ClampedArray` (8.3 MB) per kernel. **Measured (12 of the 43 kernels): 49 big allocations and 406 MB with the fixture rebuilt per kernel; 37 and 307 MB with one fixture shared (the kernels only read it: none of 43 changed a sampled byte of its input), so about a quarter of that loop's transient allocation, roughly 0.36 GB across all 43.** It is garbage the collector reclaims, so it lowers the PEAK, not a leak. `patches/p22-1085-692-fixture.patch` builds the fixture once; the test is still green at 1280 (**the rest of the suite was not run**).
- **Not done, by choice.** (1) The Squish sweeps (about 3,000 fresh 480x480 canvases): not measured, not patched. (2) The budget guard: design from the PM's note, not built. Sample `VmData` on Linux (`/proc/self/status`), a footprint figure on the Mac (`vmmap --summary` or `phys_footprint`), or `performance.measureUserAgentSpecificMemory()` in the page after a forced GC; fail a run by name when growth since the previous test passes a set budget; keep the budget out of `ship.sh` until it has been calibrated on both machines. (3) The two Mac-local branches: they need pushing before anyone can build on them.
- **Order I would do it in:** push the two local branches, then the guard (it is what makes every other number here checkable), then #1095 and #1096.
