## #1090 Work with friends: the owner's private Notes pad syncs to every guest
- **Claim: Verified (Measured).** With `project.notes` set, the view a guest is built from carries it (`FM.collab.bridge.view().project.notes`, test failure message shows the text), and `Host.validOp` accepts a write to `['P','notes']` from a guest. The PM's verdict file has the same finding with line numbers (`helper-hunts-verified.json`, F1).
- **Callers traced (Read).** `viewOfProject` (`collab-session.js:33`) is the one filter; it is used by `collab-bridge.js:116 view()`, the host base in `C.share` (`collab-session.js` about 1795), the hash (`:1037`), the snapshot parse (`:1125`), `collab-core.js:213` and `collab-ui.js:893`. So adding the key to `DENY` removes it from what is sent, from the diff and from the hash in one place. Notes are read by `notepad.js` and, on export, `app.js:5613` `confirmExport`; on a guest the reminders popped up from the owner's notes, which stops because the guest no longer has any.
- **Patch (the recommended option, owner only).** `'notes'` added to `DENY`; `Host.validOp` refuses a `P` write to any `DENY` key (`'private'`), so an older or hostile peer that still sends one is refused rather than applied; `DENY` joins the string `schemaFingerprint` hashes, `SCHEMA_REV` goes 7 to 8 and `SCHEMA_FP` is re-pinned to 5099630134268335 (the `921 S1 the schema fingerprint gate` test printed the number, and passes after).
- **Test.** `P23 #1090`: the shared view has no `notes` (CONTROL: it still has the project name, so the test is reading the share view), `Host.validOp` refuses a notes write (`'private'`), and an ordinary project-name write still passes (CONTROL). **Mutations:** `'notes'` removed from `DENY` (A1), the host check disabled (A2): both CAUGHT.
- **Cost, not hidden.** Editors can no longer share notes (that was the point of the other option). The SCHEMA_REV bump means a build before this one and a build after it **refuse to join each other** ('host-older' / 'guest-older'): everyone in a room has to be on the new version. That is the intended mechanism (the old one would diverge on the hash), but it is a real cost on the day it ships. A guest copy made earlier keeps whatever notes it already holds.
- **Open choice (the entry's ask).** The other option is to keep sharing notes and say so on the Share screens: no code change beyond one line in `PRIVACY_FULL` (`collab-ui.js:1984`). I did not build it. **Not tested end to end:** a live host and guest exchanging a snapshot (the view and the host check are the two places that decide it; I tested both directly).

## #1091 Work with friends: "Viewer: can only watch" is untrue
- **Claim: Verified (Measured for Leave).** A Viewer card with the owner's export switched off: `C.leave({keep:true})` returns a new, unlinked, editable project (test failure on main: `viewer with export off left WITH a copy: new project p_…`). The Home door (`home.js:1401`) and the Leave panel (`collab-ui.js:3189` to `3224`) are the other two doors; those are **Read**.
- **Callers traced (Read).** `C.leave` (`collab-session.js:1957`) is the one function the Leave panel and Home's live-session branch call; Home's non-live branch calls `FM.projects.detachLinked` directly. `detachLinked` is also what `detachEnded` (owner stops sharing, owner removes you) calls, with no tap.
- **Patch (the recommended option, make "only watch" true).** (1) `FM.projects.canKeepLinked(id)`: false for a Viewer or Commenter whose card says `roExport === false`, true for everyone else and for a card that never heard the setting. (2) The guest session writes the owner's `roExport` onto the linked card whenever a `settings` message arrives (`patchCollab` now accepts `roExport`), because Home has no session to ask. (3) `C.leave` refuses a keep for such a guest (resolves null, the session keeps running, nothing is taken from him). (4) The Leave panel for such a guest says what is true ("The owner turned off exporting for viewers and commenters, so this project is removed from this device when you leave") and offers Leave & delete only. (5) Home hides "Keep as my own copy" for such a card; "Leave & delete" stays.
- **Test.** `P23 #1091` (real guest session over the loop link, the card edited to a role): CONTROLS first (an editor with export off, a viewer with export on, a viewer whose card never heard it: all may keep); a `settings` message with `roExport:false` reaches the card; then for viewer and commenter `C.leave({keep:true})` returns nothing, the card is still linked, the session is not stopped; finally a viewer with export on still leaves with a copy. **Mutations:** the helper never says no (B1), commenter forgotten (B2), `C.leave` guard off (B3), the card never written (B4), `patchCollab` drops the key (B5): all CAUGHT.
- **Not covered, said plainly.** The Leave panel text and the hidden Home menu item are **Read, not run through the UI**. **A fourth door is left open on purpose:** when the owner stops sharing or removes the guest, `detachEnded` still hands him the full editable copy (no tap, no choice). Closing it would mean deleting a guest's project when the owner presses Stop sharing, which is data loss and is Ezra's call, not mine. A guest who leaves before the first `settings` message arrives is treated as allowed (Guess that the window is short; the owner sends settings on join). Cards from before this build have no `roExport` until the next time they connect.
- **Open choice (the entry's ask).** The other option is words only: change `collab-ui.js:50` to "can watch, and keep a copy" and the knock card to match. Not built.

## #1093 Images a peer sends have no pixel limit
- **Claim: Verified (Measured).** A valid 7600 x 7600 PNG (57.8 MP, 224,638 bytes, so the byte gate cannot stop it) sent by a peer is written to this device and kept (`readMedia` returns the file). On main nothing in `collab-media.js` looks at dimensions.
- **Callers traced (Read).** The peer's bytes arrive in `applyFile` (`collab-media.js` about 1114), on the owner's side as well as the guest's (a hostile editor's file lands in the owner's project too, as the verdict says). `writeRecord` stores then decodes. `planWants` already skips a file with `ctl.bad[fid]` (over the byte cap, `:716`, and the font cap); I reused exactly that, so the card says "skipped". As the PM asked, the cap is **not** in `FM.loadImageFile` (his own photos use it); the check calls it with `{still:true}` only to read the size, then releases the element and the URL.
- **Patch.** `tooManyPixels(file)` (50e6 pixels, a module constant, not added to `C.LIMITS`), called in `applyFile` for `kind === 'image'` before anything is written: over the limit it drops the parts, clears the want, sets `ctl.bad`, counts one failure and returns. A file the browser cannot decode at all is not refused here (it was not before either).
- **Test.** `P23 #1093`: one ordinary PNG and one pixel bomb announced by a peer over the real media path; the ordinary one lands (CONTROL), the bomb is not written, not in `FM.media`, and the card reports exactly one skipped file. **Mutations:** limit made unreachable (D1), check disabled (D2), failure not counted (D3): all CAUGHT.
- **Risks.** (a) **On an iPhone the size read may itself fail** (Safari will not decode a very large image into an `<img>` on some builds); then `tooManyPixels` returns false and the file is let through as it was. I could not test Safari. Reading the width and height straight from the PNG, JPEG and GIF headers needs no decode and would close that; it is a larger patch and I did not write it. (b) Video resolution is not capped (Read). (c) `writeRecord`'s other caller (`:667`, re-using a file this device already holds) is not checked, because that file is his own.
