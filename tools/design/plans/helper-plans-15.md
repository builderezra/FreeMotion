## #1041 Three or more nested styled groups draw the wrong picture (MEDIUM; ChatGPT's commit exists)
**Where (Read):** `collectGroupUnits` (compositor.js:18354) builds one `innerOf` map, "the DEEPEST unit holding this id" (:18402-18408), and `buildGroupUnit` draws a member through `u.innerOf[L.id]` (:18467-18469). With groups A>B>C all styled, C's leaves go straight to C, B never composites C, and A then draws C's leaves again.
**Callers traced:** `collectGroupUnits` is called once, from `renderScene` (:18844), which hands a top-level unit to `drawGroupUnit` (:18905); the only other entry is the recursion at :18469 (`drawGroupUnit(a, own, …)`). So one hunk in the map builder and one in the lookup covers the preview, the export and the thumbnail renders (they all go through `renderScene`). **Guess:** nothing else reads `innerOf` (I grepped compositor.js and found the three lines above only).
**What happens (Measured, `P15 #1041`):** three styled groups at opacity 0.5 each read centre red 80 where 32 is right; with a plain (transform-only) group in the middle, 128 against 32.
**Plan:** land `a22dbc46` as it is. It replaces `innerOf` with a per-unit `childOwner` built from the nearest unit ancestor (a plain group does not interrupt the chain) and looks members up there. It is one hunk of 20 lines in compositor.js.
**Test (`P15 #1041`):** equal fades at 3 and 4 deep, mixed fades (0.5 / 0.8 / 0.25) at 3 deep, and a plain group in between. **Red on main, green with the hunk, at 1280 and 380.** Mutation (Measured, results/mut_M1): the ancestry walk allowed one hop only, so a plain group ends the chain: red, "with a plain group at 1 … render 128, expected 32", the other cases still green, so the plain-group case is covered on its own.
**Not covered:** the entry's cost half (the `_flat` build count doubling per level: 4 at 3 deep, 128 at 8 deep) is not asserted, only the pixels; a middle group's blur or blend (opacity only here).

## #1042 Embedded-font import can lose a font for good (LOW; no ChatGPT commit)
**Where (Read):** `applyEmbedded` (storage.js:3742-3759) snapshots `idx = this.list()` first, awaits per font (`dataURLToFile`, face registration, `idbPut`), then `writeJSON(FONT_INDEX, idx)` (:3758) and throws away the result. `writeJSON` returns false on a refused write (:19).
**Callers traced, and this is more than the entry says:** two. `importObject` at storage.js:1713 (a whole project or template file) **and `collab-media.js:1123`, which calls it once per font as a collaborator's fonts arrive.** Two fonts arriving together interleave their awaits, so the stale-index window is not only "a picker import during a file import". The font file has been written by then (`idbPut`), so a lost index entry leaves a `font:` blob nothing lists, and `pruneOrphans` (:2958, :2987) deletes it at next boot.
**What happens (Measured, `P15 #1042`, two parts):** (a) a font imported from the picker while an embedded import is running is gone from the index afterwards ("2 listed, … missing"); (b) with the index write refused, the embedded fonts' files stay in storage with no index entry (2 orphans).
**Plan (patch, 44 lines):** collect this call's new records in a local `added`; after the loop re-read the index with no await before the write, append only families not already present (a family that appeared meanwhile has its blob deleted), write once; if the write is refused, delete this call's blobs, drop them from the session registry, and toast "Storage is full — the fonts in this file could not be saved". Uses a new `fontBlobGone(id)` helper (storage.js, next to `FONT_INDEX`).
**Test:** red on main for (a) and (b), green patched, both widths. Mutations (Measured): the orphan delete removed → red on (b); the stale snapshot restored (`idx0` read before the awaits) → red on (a).
**Not covered / flag:** the toast says "in this file", which is wrong on the collab path (one font from a collaborator): worth a neutral wording. `pruneOrphans` re-reading the id sets inside its delete pass (the entry's optional second fix) is not done.

## #1043 Picking several files makes one undo step per file (LOW)
**Where (Read):** `handleFiles` (app.js:5489) calls `FM.addMediaLayer(rec)` per file (:5495); `addMediaLayer` (app.js:3028) commits history itself (:3106). **Callers traced:** the file picker's change handler (:6918, `multiple` in index.html), drop (:8740), and the suite's `FM._handleFiles` (:5473). Voice recordings do not come through here (voice-rec.js:743 has its own audio branch), so they are untouched.
**What happens (Measured):** three photos picked together: history 1 → 4 steps, so three Undo presses.
**Plan (patch, 37 lines):** `add()` queues instead of adding; after the loop, all queued records land inside one `hist.mute()` / `unmute()` (in a `finally`) and one `hist.commit()` if any landed, re-checking `FM.stillIn` at the moment of landing. The decodes are still one by one, as before.
**A behaviour change to decide on (Guess on how it feels):** layers now appear **together, after the last file has decoded**, not one by one as each finishes. For three large videos that is a longer wait before anything shows. The alternative the entry mentions (mute the whole loop) lands each one at once but lets an edit made during a slow decode fold into the import's undo step. I chose the first because a wrong undo step is the worse failure; the builder may prefer the second.
**Test (`P15 #1043`):** three files → exactly one step, one Undo removes all three, Redo brings them back; control: one file is still one step. Red on main (1 → 4), green patched, both widths. Mutations (Measured): commit removed → red ("one picked file made 0 history steps"); mute removed → red ("3 undo steps (history 1 → 4)").

## #1044 Download names drop every non-ASCII character (LOW)
**Where (Read), five sites, not two:** `.replace(/[^\w\- ]+/g, ' ')` builds the name at storage.js:1795 (project file) and :3127 (template file), and at app.js:4283 (PNG frame), :5999 (audio export) and :6157 (video/GIF/frames export, passed on to `exporter.js`'s `download(blob, name)`). The consumers are `a.download` at storage.js:1798, :3130, app.js:4288, :6001. `audio-tools.js:16` already has a name cleaner that keeps non-ASCII (`[\\/:*?"<>|]`, `.slice(0, 80)`), so the precedent exists; its `slice` can cut an emoji pair, which the new helper does not.
**What happens (Measured):** "Привет" downloads as `project.fmotion.json`; accents and emoji are cut ("Café Noir" → "Caf Noir").
**Plan (patch, 63 lines):** one `FM.fileNameSafe(name, fallback)` in storage.js (loaded before app.js, used at call time): strips only `\ / : * ? " < > |` and control characters, removes lone surrogates, trims dots at either end, cuts at 80 code points, falls back to the old word. The five sites call it.
**⚠️ A trap I fell into and fixed in the patch:** my first version removed lone surrogates with a regex lookbehind (`(?<![\ud800-\udbff])`). **No file in js/ uses a lookbehind**, and Safari before 16.4 cannot parse one; a parse error there takes the whole of storage.js down, so the app would not load. The patch now filters `Array.from(s)` instead (a lone surrogate comes through as one unit). Keep that in mind if a ChatGPT version of this arrives with a lookbehind in it.
**Test (`P15 #1044`):** ten names for the project file (Cyrillic, CJK, Arabic, accents, emoji, `a/b:c*?` → `a b c`, `...` → `project`, a lone surrogate at either end, 90 emoji cut at 80 whole ones) and the first five again for the template file. It builds its own project (a template needs an open project with a layer; alone on a fresh page `templates.save` returns false), and puts everything back. Red on main, green patched, both widths. Mutation (Measured): the helper's class reverted to ASCII-only → red.
**Not covered (Guess):** Windows device names (`CON`, `NUL`), which stay reserved even with an extension; a name that is only illegal characters after stripping falls back, as before.

## #1045 Saving a preset on a full phone says "saved" (LOW)
**Where (Read):** effect presets: `FM.fxPresets._write` (inspector.js:372) swallows the quota error and `save` (:373) returns nothing; its callers toast success (inspector.js:2350 and :6380). Layer presets: `FM.layerPresets._write` (:564) does toast "Storage full — preset not saved", but `FM.savePresetPrompt` (app.js:5348-5349) then toasts "Preset saved — …" over it. Renames go through `_write` too (:385, :587, :597) and move the preset's tags first.
**Callers traced:** `layerPresets.save` is also called from :629 (overwrite path); `rename` is called from :6242 (`store.rename(o.name, to) && toast('Renamed…')`), which already expects a boolean.
**What happens (Measured):** with `localStorage.setItem` refusing, the toasts are ["Storage full — preset not saved", "Preset saved — apply it from any layer’s Presets section"], and the last word is "saved".
**Plan (patch, 95 lines):** both `_write`s return true/false (the fx one now toasts the storage-full line too), `save` returns that, callers toast success only on true, and a refused rename puts the tags back.
**Test (`P15 #1045`):** with storage refusing writes, saving an effect preset and a layer preset: the storage-full line appears, "saved" does not, and the preset is not listed. Red on main, green patched, both widths. Mutation (Measured): the guard in `savePresetPrompt` removed → red ("Preset saved" toast present).
**Not covered:** the rename-refusal tag restore (read, not exercised), and a refused `remove`.
