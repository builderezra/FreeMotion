## #1030 A comment's "x min ago" mixes the host's clock with the viewer's
**Where (Read, entry's lines are right):** the host stamps a comment or reply with its own clock, `v.at = now()` (collab-host.js:533, in `sanitizeComment`); the label is `ago(at)` = `Date.now() - at` in whole minutes (collab-comments.js:79-85), called once, from `byline()` at :464; the host answers every ping with its clock, `hc: now()` (collab-session.js:617), and nothing reads it (the guest's pong branch is `if (msg.t === 'pong') return;`, :814).
**What a guest sees (Read, arithmetic on `ago`):** guest clock **ahead** by 3 h: a comment stamped 5 minutes ago reads "3 h ago"; guest clock **behind** by 3 h: it reads "just now" (the difference is negative, `!(m >= 1)`), for the next three hours. **The entry's test idea ("guest clock 3 h behind: a fresh comment reads 'just now'") is already true on main** (fresh comment, behind clock reads "just now" by accident), so it would not fail; the case that shows the bug is a 5-minute-old comment, either way. Also: the guest's own new comment is stamped with the GUEST clock at :137 and :154 (`at: Date.now()`) until the host's copy overwrites it with the host's, so a guest with a skewed clock sees its own comment's age jump when the host's version arrives.
**Callers traced:** `ago` has one caller (:464). `at` is also read by the two sorts (:489, :490, all host-stamped, so order is unaffected), `collab-host.js:441` and `:483` (the removed-comment record and its restore, same host clock), and not by presence (`p.at` in collab-presence.js:330 is a local receive time) or media (`rec.at`, collab-media.js:1460, a different thing). Pings go out only with liveness on (`liveTick`, collab-session.js:1482-1492, every `LIM.PING` = 2000 ms, collab-core.js:64), and every guest turns it on: collab-ui.js:3844, :3950, :4538, :4553.
**Plan:** the guest keeps `hostOff = msg.hc - now()` from the latest pong (off by the one-way delay, under a second against a label in minutes: no round-trip algebra needed) and offers `S.hostNow() = now() + hostOff`; the owner's `hostOff` stays 0, so alone and on the owner's device nothing changes. The comments module reads one helper, `hostNow()`, for `ago` and for the two creation stamps. Zero until the first pong, which is exactly today's behaviour for the first two seconds. No wire change (`hc` is already sent), so no schema bump. 12 lines in the patch.
**Test (`P13 #1030`):** the S6 harness with fake clocks, the guest's clock 3 h behind then 3 h ahead of the host's: CONTROL that before any pong the guest reads its own clock; after one ping and its pong `G.hostNow()` is within 50 ms of the host's; a comment stamped 5 minutes ago reads "5 min ago" through `CM._ago(at, G.hostNow())` while CONTROL says the raw guest clock does not. **Red on main ("the guest has no estimate of the host clock"), green with the patch.** Note the base time is 100,000,000 ms on purpose: a guest clock 3 h behind a small fake time goes negative and `lastPing = 0` then never fires (I lost ten minutes to that).
**Not covered:** a real second device (Tier 3 frames); the owner's clock being wrong is by definition the reference, so nothing to fix there.

## #1031 GIF and PNG-frame exports never offer the share sheet
**Where (Read):** `download(blob, name + '.gif')` at exporter.js:1730 (end of `runGif`) and `download(zipBlob, base + '_frames.zip')` at :1800 (end of `runFrames`); `download()` is an `<a download>` click (:47-53). The MP4 goes through `deliver()` (:66) and, when the caller passes `onReady`, through the ready card (`showExportReady`, app.js:6242), whose Save is a **fresh tap** so `navigator.share` has the transient activation a long render has lost (the comment at exporter.js:51-58 and app.js:6226-6240 says exactly this).
**Callers traced:** `runGif` and `runFrames` are called from app.js:6188 and :6190 only (plus tests: tests.js:80782, 80783, 89165, 91566, none passes `onReady`, so they keep the plain download). `deliver()` has two callers, both the MP4 (exporter.js:1623, :1626). `showExportReady` has one caller (app.js:6193) and a suite seam. **`deliver()` hard-codes `type: 'video/mp4'`**, so it cannot be reused as is for a GIF or a zip; the patch gives it a `type` argument and the MP4 call passes none.
**What he gets (Guess for iOS; I cannot run Safari):** on iPhone a GIF made by the exporter lands in Files; through the share sheet "Save Image" puts it in Photos. A PNG-frames **zip** cannot go to Photos either way (sheet offers Save to Files, AirDrop, apps): the gain there is the card and the fresh tap, not Photos. He may want the zip left on plain download; it is a one-line difference in the patch.
**Plan (in the patch, 3 hunks):** `runGif` and `runFrames` call `opts.onReady({ blob, name, poster: null, width, height, fps, seconds, noSound: true, save })` when given one, else `download()` as before; `save` is `deliver(blob, name, 'image/gif')` or `'application/zip'`. app.js passes `onReady: showExportReady` for both, and the "Done - saved to your Downloads" line (which would be a second, often wrong answer behind the card, as the existing comment says for the MP4) goes: every format now ends by hiding the overlay. The card's meta line would otherwise end "... no soundtrack" on a GIF, so the card takes `noSound` and drops that clause. `showExportReady` already tolerates a missing poster and any `out.hasAudio`, and falls back to `out.save()` when the page has no card.
**Test (`P13 #1031`):** through the real export (`exp-format` = gif, an 80 x 60 project of 0.4 s): the ready card must appear with no straight download and no share yet; Save then offers exactly one File to `navigator.share`, type `image/gif`, name ending `.gif`, and no download; then `runFrames` with `onReady` hands `save()` a File of type `application/zip` named `..._frames.zip`. `navigator.canShare/share` and `HTMLAnchorElement.prototype.click` are stubbed and restored. **Red on main: "the GIF export finished with no ready card: 1 straight download(s) (Untitled.gif), share called 0 time(s)"; green with the patch.**
**What it breaks (Measured, found by running the neighbours, not by reading):** `690 a Custom size set in the export dialog is the size of the GIF and of the PNG frames, the project contained in it` (tests.js:91802) presses Export for a GIF and a frames zip and waits for the download link; with the card in front, the link is only written when Save is pressed, so it fails "setup: the gif export handed nothing to the download link". The repair is in `p13-1031-existing-test-adapt.patch`: the wait loop presses `#xr-save` when the card is up (Save falls back to the download link where there is no share sheet, as for the MP4). **The tests that call `runGif` and `runFrames` directly (tests.js:80782, 80783, 89165, 91566) pass no `onReady` and are untouched.** Any other code or test that presses Export for a GIF and waits for a file has the same dependency; I found no other in the suite.
**Needs his eye:** it changes what the last screen of a GIF export looks like (the card in front, Save / Discard) and "Discard" now exists for a GIF. Show him the card with a GIF in it before shipping.

## #1034 Test gap: a GIF over the memory budget is shrunk, drawn full size, and freed on removal
**What the code does (Read):** `decodeGifAnimation` (media.js:720) keeps every frame as a bitmap of `W x H x 4` bytes and scales them by `k = min(1, sqrt(gifBudget() / (W*H*4*n)))` (:727); `gifBudget()` is half the frame-cache limit clamped to 32-160 MB (:639-642). The compositor draws the picked frame into the clip's own `cw x ch` (compositor.js:17760, :17767), not at the bitmap's size, so a shrunk frame is stretched back (softer, never smaller). `release()` closes the frames (`closeAnim`, media.js:59, defined :793), and `FM.media.set` releases whatever it displaces (:66-68). **Existing coverage (Read):** the GIF tests use fixtures of 4 x 4 to 96 x 64 (tests.js:92700-92870), so the shrink never runs.
**Test (`P13 #1034`, green on main):** a 2800 x 2800 GIF of six one-pixel frames (the existing `h3aGifBytes` builder; 188 MB decoded, over the 160 MB ceiling on any device). It asserts: frames shrunk (here 1870 x 1870, not 2800) and not absurdly (over 100); the clip's loaded size is still 2800 x 2800; rendering the layer calls `drawImage` with the decoded frame and a **destination of 2800 x 2800** (spied on the real context, both the 5- and 9-argument forms); CONTROL that all six bitmaps are open; replacing the media releases the old record, all six are closed (`width === 0`), and `rec.anim` is null. It builds the layer by hand (`FM.makeLayer('image')` + `FM.media.set`) rather than through the importer: the importer path was flaky here (the media record was gone by the time the test looked, which is its own question, **not chased**).
**Mutation-checked (Measured), three:** shrink off (`const k = 1;`): "kept its frames at 2800 x 2800: the memory budget never shrank it"; `closeAnim` not called in `release`: "6 of 6 decoded frames were still open after the clip was replaced"; the compositor drawing at the bitmap's size (`src.width, src.height` for `cw, ch`): "drawn 2644 x 2644 instead of the clip's full 2800 x 2800". All restored. About a second to run, but it holds roughly 190 MB of bitmaps while it does.
