## #1046 An AI batch that deletes a layer takes 2+ undo presses (LOW)
**Where (Read):** `applyOps` (js/ai-ops.js:127) never mutes history; its `deleteLayer` op (:446-451) calls `FM.deleteLayer`, which commits for itself (app.js, the outermost call). ai-chat.js's `applyTurn` brackets its call with `history.mute()`, ai.js does not.
**Callers traced:** `applyOps` is called from ai-chat.js:135 (muted already; the depth counter nests), ai-templates.js:85 (then commits), and ai.js at :211 (Director scaffold, commit at the end of the run), :229 (each builder), :266 (the critic's fix ops), :338 (re-roll) and :387 (Refine). Every one of the ai.js sites does `refreshAll` + `commit` itself after the call, so muting inside `applyOps` loses no commit. The model can send `deleteLayer` through any of them (`ai-manifest.js:45`); the built-in mock only does it for the chat path (`ai-mock.js:116`), not for Refine.
**What happens (Measured, `P16 #1046`):** edit A, delete B, edit C then `refreshAll` + `commit`: **2 undo steps** on main, and the first Undo leaves the scene half-undone.
**Plan (patch, 14 lines):** `applyOps` becomes a wrapper that `mute()`s and `unmute()`s in a `finally` around the old body (`applyOpsBody`), so no caller can forget. Also in ai.js (the Director's cancel path, :291): commit always, not only when the layer count changed (an identical snapshot is a no-op in `history.commit`, Read at history.js:275-300), so a cancel after a build that deleted one layer and added one is not left uncommitted. **That second half is Read, not exercised:** the Director's cancel path needs the whole orchestrator.
**Test:** red on main (made 2 steps), green patched at 1280 and 380; control: a plain edit batch is one step. Mutation (Measured): the `mute()` removed → red, "made 2 undo steps".

## #1047 Mask picked first, then another effect, is 2 undo steps (LOW)
**Where (Read):** `addMaskFromBrowser(quiet)` (fx-browser.js:558) ends with `FM.history.commit()` even when `quiet`; `commitPicks` (:509) commits once more at its end.
**Callers traced:** `addMaskFromBrowser` is called from the Mask tile's click (:610, never quiet: the single-tap path) and from `PSEUDO_ACTION._mask` (:637), which only `commitPicks` calls, with `quiet = true`. So only the batch path changes. `commitPicks` is reached from Done, the X, the backdrop, the tabs, a preset row and the commit bar's Add (:670, :1636, :1728, :1884, :1909).
**What happens (Measured):** pick Mask, then Gaussian Blur, then Add: history +2, and one Undo takes only the second effect. Blur first then Mask is +1 (the control, green on main).
**Plan (patch, 1 line):** `if (FM.history && !quiet) FM.history.commit();`.
**Test:** the real sheet at 380 (picks by tile click, the commit bar's Add); asserts +1 step and that one Undo removes both. Red on main, green patched. Mutation (Measured): the guard removed → red.

## #1048 A long unbroken text run wraps in quadratic time (LOW)
**Where (Read):** `FM.textLines` (compositor.js:19042), the `chop` helper: `trim(s)` and `fits(trim(s))` measure the whole remainder for every line, then a one-character walk with `fits(slice(0, cut + 1))`.
**Callers traced:** four, all through this one function: compositor.js:15128, :16586, :17416, :19168 (the draw pass, the footprint pass, the layer size). Import does not cap text length (storage.js:1638-1650, Read).
**What happens (Measured, `P16 #1048`):** wrapping 30,000 characters with no spaces at width 300 measures **15,509,505 characters (517 per character)** on main.
**Plan (patch, 18 lines):** find the longest fitting prefix by doubling then bisecting; never more than about two lines of text is measured at once. **With the patch: 190,869 characters (6 per character), 81 times fewer** (Measured by lowering the test's limit to 0 and reading the message).
**⚠️ The cut points are the same only while prefix width is monotone** in length. A font whose widths are not (a ligature or a combining mark can make a longer prefix narrower) could cut one character differently from the old walk. The suite finds no difference: **88 layouts** (11 inputs × 4 widths × 2 sizes: 1,000 `x`, a 300-letter word between spaces, mixed `i`/`M`, Japanese, Japanese inside English, emoji, accents with combining marks, paragraphs with blank lines, one character, empty, a column narrower than one letter) are compared line for line with the old algorithm, which the test carries verbatim. A **Guess** on other fonts. Optionally clamp imported text to about 20k characters (not done).
**Test:** red on main (cost, 517 vs the limit of 40 per character), green patched. Mutations (Measured): the bisect direction flipped → red (49 of 88 layouts differ); the doubling replaced by measuring the whole remainder → red (the cost, 1,005 per character).

## #1049 The boot sweep and project delete fail open on unreadable indexes and save points (LOW, total loss when it happens)
**Where (Read):** `list()` for templates, elements and fonts is `readJSON(INDEX, [])`: damaged JSON reads as `[]` (storage.js:3069, :3412, :3674). `pruneOrphans` (:2929) builds `tplIds` / `elemIds` / `fontIds` from them, so every pack is a candidate, and `collectKeep` (:2935) reads each `fm.proj.*` doc with `readJSON(lk, null)`, so a damaged doc keeps nothing. `idbGet` (:175) resolves null on error, so a checkpoint whose read failed adds no ids to `ckptKeep`. `projects.remove` (:2856) builds `elsewhere` from the same readers. Writers (`writeJSON(INDEX, this.list().filter(...))`, :3135, :3589, :3724, and the project index) overwrite the damaged bytes with `[]`.
**Callers traced:** the sweep is called once, at boot (app.js:6877); `projects.remove` from the project card's delete and from the suite; the three `list()`s have 61 call sites in storage.js alone, which is why the patch changes only the readers the sweep and the delete use, and `writeJSON`, not `list()` itself.
**What happens (Measured, three tests):** (a) with `fm.templates`, `fm.elements` and `fm.fonts` damaged, the sweep deletes `tpl:`, `elem:` and `font:` packs; (b) with the save point's read failing, the sweep deletes the one blob only the save point names; (c) deleting project A deletes the blob a truncated project B still uses. All red on main, each with its control (a valid empty index collects the packs; a readable save point keeps its blob; no other document deletes the blob, a readable one keeps it).
**Plan (patch, 59 lines):** `readStrict(key, kind)` answers `{ok, val}`: absent is `ok` with null, damaged or the wrong shape is `ok: false`. `idbGetStrict` likewise. The sweep: an unreadable index keeps every pack of its kind; an unreadable project doc or save point sets `unsafe`, and **the sweep deletes nothing this boot**. `projects.remove`: an unreadable other document or save point stops its blob deletes (`unsafeRemove`). `writeJSON` on the four index keys first keeps one copy of an unreadable value at `<key>.unreadable` (once).
**Decision for him (Guess on how it feels):** a document that is damaged for good makes the sweep stand down at every boot until it is repaired or removed: the leak is the price, as for the shared `lib:` copies. There is no UI that says so. The `.unreadable` copy is kept once and never cleared.
**Test:** three tests (above), red on main, green patched. Mutations (Measured): the unreadable-index guard removed → red (a); the save-point `unsafe` removed → red (b); `!unsafeRemove` removed → red (c); `preserveUnreadable` made a no-op → red (c's copy half).
**Not covered:** a damaged **project doc** at the boot sweep (the `unsafe` line in `collectKeep` is Read, not exercised), a failed `idbGet` for a non-checkpoint key, and the entry's per-layer delete in `projects.remove` for a project that is the open one.

## #1050 Recent colours: each window overwrites the other's picks (LOW)
**Where (Read):** `FM.recentColors` is hydrated once at init (inspector.js:6977); `addRecentColor` (:247) writes `[c]` + that memory and never re-reads.
**Callers traced:** `addRecentColor` is only called by `colorField`'s `commitColor` (:265), which every colour box in the inspector and the text editor builds (8 `colorField(` call sites; exported as `FM._colorField` for the suite).
**What happens (Measured):** this window holds `['#aaaaaa']`, the other stores `['#112233']`, a pick of #445566 here stores `#445566,#aaaaaa`: the other window's colour is gone.
**Plan (patch, 9 lines):** `storedRecentColors()` reads and validates the stored list; `addRecentColor` merges into **that** (falling back to the memory when the stored value is damaged), and a colour field re-reads it when it is built, so a popover opened after the other window picked shows the pick.
**Test:** the pick with the popover already open (the memory is stale), then a popover built afterwards, then damaged stored data as a control. Red on main, green patched. Mutations (Measured): no re-read in `addRecentColor` → red (the first version of the test **survived** this, because building the field refreshes the list too; the test now builds the field first and changes storage after, which is why there are two mutations); the refresh in the field build removed → red.
