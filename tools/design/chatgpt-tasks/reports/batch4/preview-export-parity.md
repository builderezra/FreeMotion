# Preview and export parity review

Snapshot: `28104a3e83e01ac3880db3fac604a7444c7235aa`

Scope: source inspection of the preview caller in `js/app.js`, the shared renderer in `js/compositor.js`, and the MP4 frame loop in `js/exporter.js`. **Read, not run:** I did not launch the app, render comparison frames, or run tests. The visual magnitude of renderer branches below is therefore UNVERIFIED unless described as a direct code-path fact.

## Confirmed render-path differences

1. **Motion Flow uses a different analysis resolution in preview and export.** In `js/compositor.js:12862-12869`, the kernel says `// STYLE 0: PIXEL MOTION — per-pixel blur along the local flow vector, at a capped working res` and sets `const WW = Math.min(FM._exporting ? 720 : 480, W)`. The MP4 path sets `FM._exporting = true` at `js/exporter.js:1251`; preview renders without that flag. Thus, when the layer working width exceeds 480 pixels, export can analyse the flow field at up to 720 pixels while preview caps it at 480. Different flow sampling can change which pixels are treated as moving and the resulting smear. It is most relevant to large/high-detail layers with Motion Flow active; at widths of 480 or less both paths use the same cap. **Confidence:** high that the code takes different branches; UNVERIFIED how visible the difference is in a particular project.

2. **The editor can show an uncommitted effect preview which export deliberately omits.** `js/compositor.js:2005-2008` reads the preview stack only when `!FM._exporting`: `if (FM._exporting) return null;` and otherwise returns `pv.list` for its matching layer. Export sets that flag at `js/exporter.js:1251`. If a user has selected an effect/filter tile for live preview but has not added it to the layer, the canvas includes the candidate and the exported file does not. This is a temporary editing state, not a committed-effect rendering mismatch. **Confidence:** high for the branch; UI reproduction not run.

3. **Video seeks may show a stale held frame in the editor while export skips that frame.** `js/compositor.js:17181-17187` says that when `readyState < 2`, preview substitutes `m._lastFrame` if available, but export returns without drawing it: `if (!FM._exporting && m._lastFrame && m._lastFrame.width) src = m._lastFrame;`. During a slow scrub/seek, the editor can temporarily show the previous decoded frame; export does not bake that stale image and may leave the layer absent for that sample if it is still undecoded. The export loop seeks and immediately calls the renderer at `js/exporter.js:1475-1479`: `await seekAllVideos(scene, t); FM.renderScene(projCtx, scene, t);`. **Confidence:** high for the explicit branch; the frequency and export impact of a seek not being ready are UNVERIFIED and depend on media/device decode timing.

4. **Motion Flow's preview-scale pixel grid differs from its export grid even below the cap.** Shared rendering stamps a preview canvas scale at `js/app.js:654-660`: `w = Math.max(1, Math.round(P.width * s)); ... canvas.__fmRS = s`. `plateScale` in `js/compositor.js:3811` returns `Math.min(1, ctx.canvas.__fmRS || 1)`, while export uses a project-sized canvas at `js/exporter.js:1235-1237`: `projCanvas.width = P.width; projCanvas.height = P.height;`. The compositor explicitly documents that pixel-measured effects can read differently on a reduced preview at `js/compositor.js:3808-3810`: `The cost is that effects measured in PIXELS (grain size, scanline pitch, tile size) scale with the plate, so they read slightly differently in a reduced preview.` This means the canvas while playback quality is reduced is not a pixel-identical reference for pixel-scale effects; the editor restores its stopped quality via `js/app.js:2655-2657`. This is a reduced-playback-preview limitation; I did not identify a new single kernel failure here, and the size of any visual difference is UNVERIFIED.

## Preview-only picture and endpoint behavior

These are explicit view/editor conveniences and intentionally are not part of the rendered file:

- The preview draws a caption in its settled form while the user is typing, and draws onion skin, guides, and canvas-edit overlays after the scene. The caller is `js/app.js:103-126`; the code says `THE CAPTION HE IS TYPING IS DRAWN AS IT LOOKS ONCE IT IS IN — THE PREVIEW ONLY` and calls `drawOnionSkin()`, `drawGuides()`, and `FM.canvasEdit.update()`. The exporter calls `FM.renderScene` directly at `js/exporter.js:1479`, so these editor overlays are not in the MP4. The typing-cue display is intentionally temporary; the visual overlays are editing aids.
- An isolated layer is preview-only: `js/compositor.js:18371-18372` guards it with `!FM._exporting`. A crop under active editing also shows the full source frame only in preview: `js/compositor.js:18524-18527` uses `layer._cropEditing && !FM._exporting`. The project’s committed crop is what exports.
- At an exact layer-end instant with no incoming layer, the preview nudges the sample backward by (0.0001) seconds; the export samples its exact frame times and retains the half-open clip interval. The preview call is `js/app.js:122`: `FM._endInstantTime(FM.scene, FM.time)`; the exporter uses `const t = start + f / fps` at `js/exporter.js:1477`. This only affects a parked playhead precisely on an otherwise empty boundary; at a cut with an incoming layer the preview helper leaves the time alone.

## Other requested dimensions

- **Blend modes:** both paths call the same `FM.renderScene` on the same scene object (`js/exporter.js:1479`), and the shared compositor applies layer blend modes in that path. I found no separate preview/export blend-mode branch in the traced call path. This is source inspection, not pixel-comparison execution.
- **Text fonts and wrapping:** both paths use the shared compositor, so they use the same canvas text/layout code. The preview canvas and export canvas have different backing scales, and browser font rasterization can vary by platform; no font-specific branch was confirmed in this review. Pixel-level equality is UNVERIFIED.
- **Animated effects and frame rate:** export evaluates the shared scene at `start + f/fps` (`js/exporter.js:1475-1479`); preview passes its current playhead time to the same renderer (`js/app.js:122`). A different preview frame cadence can therefore sample an animated effect at different instants while playback is in motion. I did not confirm a separate effect-clock formula in the preview/export call sites.

No browser/device render comparison was run. Findings about visible severity, decode timing, and platform font rasterization remain UNVERIFIED.

## Audio timing supplement (source inspection; not run)

The audio paths use different clocks and sample-generation strategies, so they are a separate parity risk from the shared video renderer:

- Forward-clip preview lets the media element play its own audio: `js/app.js:2216-2220` says `Forward clips free-run their own <video> audio` and obtains `local = FM.layerLocalTime(layer, FM.time)`. The live sync controller can seek that element to `local` or adjust its rate (`js/app.js:2357-2367`: `if (plan.action === 'seek') { m.el.currentTime = local; ... } ... m.el.playbackRate = plan.rate`).
- Export decodes/resamples each clip into an offline mix rather than recording those live elements: `js/exporter.js:477-485` sets `const sampleRate = 48000, channels = 2` and creates `new OAC(channels, length, sampleRate)`. The mix’s output-time offsets are calculated from `sceneT - from` at `js/exporter.js:622-627` (`const ot = Math.max(0, sceneT - from)`). Exported ramped clips map output samples through `FM.layerSourceAdvance` at `js/exporter.js:317-331`; ordinary-rate clips use `FM.srcSampleAt` at `js/exporter.js:344-352`.
- Reverse preview synthesizes a Web Audio source and starts it at the playhead offset: `js/audio-play.js:171-181` reads `FM.time - layer.start`, assigns `node.playbackRate.value = FM.previewRate || 1`, and schedules the gain. Export instead constructs reversed samples in `js/exporter.js:344-352` and `js/exporter.js:360-362` (`return reversed ? (startSample + (lenSamples - 1 - i) * speed) : ...`).

These are confirmed source-level branch differences: live element synchronization versus offline sample placement, and Web Audio reverse playback versus reversed sample generation. They can be exercised with forward/reversed clips, non-1x speed, and sub-range exports. I did not run an audio comparison or measure drift, so whether these current paths produce an audible parity error on a given browser/device is **UNVERIFIED**; this supplement does not claim a new audio bug.
