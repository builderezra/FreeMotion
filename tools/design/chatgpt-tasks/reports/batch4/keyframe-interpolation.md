# Keyframe interpolation review

Snapshot: `28104a3e83e01ac3880db3fac604a7444c7235aa`

Scope: source inspection of interpolation/easing in `js/scene.js`, easing families in `js/eases.js`, and the clip split path in `js/app.js`. **Read, not run:** I did not launch the editor, sample rendered frames, or run tests. The examples below are hand-evaluated from the source; visible timing/motion on a real project is not runtime-verified.

## Confirmed behavior and user-visible limitations

1. **Rotation uses direct numeric interpolation, not shortest-angle interpolation.** The common numeric path in `js/scene.js:127` is `return a.v + (b.v - a.v) * f;`. There is no angle wrap or normalization in `evalProp`. For rotation keyframes 350° → 10°, halfway evaluates to 180°, taking a 340° reverse turn rather than the +20° short route. Conversely, 0° → 720° intentionally permits two full turns. This is a limitation only when the user expects wrapped angles to take the short route; explicit multi-turn animations depend on preserving raw numeric deltas. **Confidence:** high for math; no playback test run.

2. **Colour keys interpolate encoded RGB channel bytes, which can produce dark/muddy midpoints.** `js/scene.js:46-51` defines `lerpHexKf`; its channel calculation is `Math.round(A[i] + (B[i] - A[i]) * f)`, then returns a hex colour. `evalProp` selects it for string-valued keys at `js/scene.js:110`: `if (typeof a.v === 'string' || typeof b.v === 'string') return lerpHexKf(a.v, b.v, f);`. Thus #ff0000 → #00ff00 gives #808000 at the midpoint (olive), with no linear-light or perceptual colour-space conversion. This is directly confirmed by the arithmetic; whether a particular transition reads as “muddy” is subjective. **Confidence:** high for channel interpolation; no display test run.

## Checked cases with no new defect confirmed

- **Easing endpoints:** the scalar ease functions in `js/scene.js:30-38` map 0 to 0 and 1 to 1; cubic Bézier explicitly returns 0/1 for inputs outside or at its endpoints at `js/scene.js:56-58`. Parameterised families document exact endpoint invariants in `js/eases.js:23-26`; the inspected bounce, elastic, cyclic, random and steps functions implement endpoint handling at `js/eases.js:47-49,57-64,69-80,83-97`. Overshoot/anticipate can exceed the keyframe values between endpoints by design. I did not execute an endpoint sweep.
- **Hold/step keys:** the segment’s easing belongs to its ending keyframe, as stated at `js/scene.js:24-27`. A hold segment returns the starting value until the exact ending key time, then returns that ending key’s value: `js/scene.js:88-93` contains the inclusive interval and `if (b.e === 'hold') return (t >= b.t) ? b.v : a.v;`. Parameterised Steps clamps the final value to 1 at `js/eases.js:83-87`. No new off-by-one defect was confirmed by inspection.
- **Keys exactly on cuts/splits:** `js/app.js:5061-5083` retains keys on the corresponding side with a small tolerance, adds a seam only when no nearby key exists, copies the ending key’s easing metadata, and sorts the result. The implementation has specialized handling for shape-point arrays at `js/app.js:5037-5050`. I found a prior audited split-easing issue during the required skip search, so I did not re-report or retest that topic.
- **Very close keys:** `evalProp` scans adjacent sorted keys and treats non-positive spans as progress 1 at `js/scene.js:88-94`; ordinary positive sub-frame spans use the fractional time between the keys. The editor’s evaluation is continuous, but playback/export only sample rendered times, so key changes faster than the output frame interval may not appear as separate visible states. No new failure was confirmed; a sub-frame imported project was not executed.
- **Speed-keyed clips:** speed values are evaluated through `FM.speedAt` at `js/scene.js:976-997`. Source advancement for animated speed is precomputed on a 120 Hz table and linearly interpolated at `js/scene.js:953-971`; specifically `const SR = 120` and the table uses trapezoidal accumulation `acc += (prev + v) / (2 * SR)`. This is an approximation to the integral of the evaluated ramp. It could matter for unusually sharp/non-smooth ramps or high frame-rate sampling, but I did not measure an error and do not classify that as a confirmed defect. Speed-range changes that rescale keyframe times were not re-audited here.

No runtime execution was performed. Apart from the direct numeric-angle route and byte-channel colour interpolation above, I found no additional confirmed interpolation defect in the requested cases.
