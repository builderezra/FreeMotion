Add a short "Corrections" section at the top of each report rather than rewriting it. H1 especially: the 8.7 GB was VmData (address space reserved against a data ulimit on Linux), not resident memory. Say so, and re-scope the guard.

## [WRONG] H1 claim 1: 'I could not reproduce 8.7 GB'. Renderer RSS (resident memory) peaked at 1085 MB and virtual size was 1.4 TB, so 'the suite itself does not need that much'.
**Problem:** The method does not match the original figure. The 8.7 GB was VmData, the data segment that the Linux renderer sandbox caps at 8 GiB (RLIMIT_DATA). It is neither RSS nor VmSize. Commit ca74942c (6 Oct, before H1) quotes the kernel line 'VmData 8760119296 exceed data ulimit 8589934592' and its _cdp.py note says 'it was 8.7 GB of RESERVED data, not resident memory'. H1's numbers (1.1 GB RSS, 1.4 TB VmSize) and the 8.7 GB VmData can all be true at once, so 'not reproduced' is not a finding. H1's own guard (section 4) reads VmRSS from /proc/<pid>/status, the same file that holds VmData, and never reads VmData. On the Mac RSS is the wrong number entirely: the 7 Oct stall had the test Chrome 'squeezed to under 1 MB resident' with swap at ~7 of 8 GB, so an RSS budget would pass at the very moment the Mac is drowning. H1 did correctly note that the driver is headless and asked which metric was meant. Its 'headed browser' guess does not apply, because _cdp.py launches --headless=new everywhere. Its hang at test 1924 matches how a sandbox-cap crash looked on b46b47d3's driver, which has no Inspector.targetCrashed and waited silently, but it reported flat 948 MB memory. Nobody checked dmesg for 'exceed data ulimit' or whether the renderer process was still alive, so the cause is unknown.
**Fix / replacement:** Sample VmData alongside VmRSS (same /proc/<pid>/status read), and check `dmesg | grep 'exceed data ulimit'` at any hang. On the Mac, read phys_footprint (`footprint -p <pid>` / `vmmap -summary`), never ps RSS. Base the budget guard on VmData (Linux) or footprint (Mac). An RSS-only guard cannot catch either the Linux crash or the Mac swap stall.
**Evidence:** git show ca74942c (commit message; tests/_cdp.py docstring lines ~90-96); REQUESTS.md:35460 and :35649 ('died on Chrome's 8 GB renderer cap'); REQUESTS.md #1085 7 Oct note ('under 1 MB resident ... swap ~7 of 8 GB'); b46b47d3:tests/_cdp.py:44 (--headless=new, no --no-sandbox, no targetCrashed); H1 report section 0 and section 4 step 1 (VmRSS only).

## [FIX] H5 claim 1 (M2, ranked HIGH): Motion Flow, Time Warp Scan, Frame Stutter and Temporal Denoise move their state on once per rendered frame with no time-between-frames scaling. The preview 'renders at the display's rate (60 or 120 times a second)' while export renders at fps, so the two differ.
**Problem:** The mechanism is confirmed but the premise is wrong. Confirmed: Motion Flow advances once per render (compositor.js:13235), Echo uses a constant persist (:13272), Frame Blend a constant alpha (:13260), and Temporal Denoise advances at :12724 with a fixed 0.5×strength blend at :12790. Nothing is scaled by the time step. Wrong: playback draws at most ONE canvas frame per PROJECT frame. tick() computes fno = floor(t·fps) and renders only when it changes (app.js:2484-2486), and its comment says it 'stops repainting an identical frame twice on a 60 Hz screen showing 30 fps'. Video 'seeked' repaints are suppressed during play (app.js:3075). So in steady playback the preview takes the same number of steps as an export at 'Same as project'. The real divergences: (a) frames dropped on a slow phone (app.js:2486 counts them), each one a missing step and a wider gap, so Echo fades more slowly per second and Frame Blend/Smear compare against an older frame; (b) an export frame rate different from the project's (index.html:891 #exp-fps); (c) preview times sit off the frame grid by up to one frame (minor). Frame Stutter is misclassified: it re-captures only when its clock-derived quantum q changes (`if (rec.t !== q)`, compositor.js:13193). The only difference is which moment the first render in a hold captures, so HIGH is overstated. Time Warp's strips (:12900-12906) differ only under (a) or (b). The proposed fix ('advance only when the project frame number changes') is essentially what playback already does and would not fix (a) or (b). The proposed 1/30 vs 1/60 test models a case that does not happen in playback.
**Fix / replacement:** Scale each step by the real time step: Echo fade = persist^(dt·fpsRef), Frame Blend alpha and Denoise weight likewise, and a gap well beyond a frame counts as a drop, not a step. Test: render 2 s at 30 fps once with every frame and once with every other frame skipped (a 15-step run standing in for dropped frames), plus once with export fps 24 on a 30 fps project, and compare the last frame within a measured tolerance. Downgrade Frame Stutter to LOW-MEDIUM (its only difference is a hold entered mid-way by a scrub or a dropped frame).
**Evidence:** app.js:2442 tick, :2483-2486 (one draw per project frame, drop counter), :2505-2506 (UI per rAF), :1716 (smooth clock), :3075 (seeked guarded by FM.playing); compositor.js:12724, :12790, :12900, :12906, :13193, :13235, :13260, :13272; exporter.js:1468/1477 (t = start + f/fps); index.html:891.

## Reviewer summary
I checked all three hunt reports against b46b47d3, reading only. Most of their line references are right. Each report has one central claim that is overstated or rests on a wrong premise.

**H1 (suite memory):** The 8.7 GB figure was never resident memory. Commit ca74942c quotes the kernel line "VmData 8760119296 exceed data ulimit 8589934592" and calls it "RESERVED data, not resident memory". H1 sampled only resident memory (RSS) and total virtual size, never VmData. So "could not reproduce" compares two different numbers, and the results do not contradict each other. Its proposed guard would also use RSS, which on the Mac falls exactly when the Mac is short of memory. The 250-300 MB "leak" was sampled without a forced garbage collection. "Pools only grow" is true only of `_fxScratch`; the pool canvases resize to the exact size on every use.

**H5 (preview vs export):** The mechanism is real: Motion Flow and Temporal Denoise move their state on by one fixed step per render, with no allowance for time between frames. But the stated cause is wrong. `tick()` draws at most one frame per project frame (app.js:2484-2486), so the preview does not render at 60/120 Hz. The real causes are frames dropped on a slow phone and an export frame rate that differs from the project's. Both the proposed fix and the proposed 1/30 vs 1/60 test therefore miss. Frame Stutter is wrongly rated HIGH: it advances on the clock, not per render. The 480 vs 720 branch exists (compositor.js:13354), but it sets the size the Pixel Motion blur is drawn at, not the motion analysis, which is 160 px in both (:12285). The record cache holds 13 entries, not 12.

**H6 (phone performance):** All four per-frame paths exist and run on every animation frame, outside the once-per-project-frame draw check. They sit at app.js:2505-2506, not the cited 2487-2488. Much of the cost is overstated because writing an unchanged value or toggling a class that is already set costs little. The real per-frame costs are each clip label's `maxWidth`, a layer lookup that grows with the square of the layer count, and two forced layouts per frame in canvas-edit.js. Those forced layouts happen when the selected layer moves, or when the rotate knob has been moved because it would sit off the stage (a portrait clip filling the frame on his phone). That case is worse than H6 says.
